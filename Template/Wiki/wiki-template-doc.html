THEAI Monitoring & Vulnerability Platform

En une phrase. Application de supervision de serveurs et d'évaluation de vulnérabilités (React + FastAPI + PostgreSQL). Surveillance temps réel via ICMP, TCP, HTTP/HTTPS et SSH, avec tableau de bord de sécurité.

1. Vue d'ensemble

Monitoring

  • ICMP : connectivité + temps de réponse
  • TCP : disponibilité sur ports personnalisés
  • HTTP/HTTPS : ports et chemins personnalisés
  • SSH : disponibilité, authentification supportée
  • Historique des statuts et temps de réponse
  • Contrôles périodiques configurables

Sécurité

  • Quick Scan (synchrone, 5 à 15 s) : ports critiques + TLS
  • Full Scan (asynchrone) : ports étendus, services, protocoles
  • Niveaux Critical / High / Medium / Low
  • Recommandations de remédiation
  • Historique persistant (audit, tendances)
  • Authentification JWT

4. Installation

Kubernetes (recommandé en production) : Helm chart et documentation sur iwebbo.github.io/THEAI.

4.1 Docker (pas à pas)

  1. Cloner le dépôt et créer le réseau : 
    git clone https://github.com/iwebbo/THEAI
cd THEAI
docker network create theai-net
  2. Base de données : 
    docker run -d \
  --name theai-db \
  --network theai-net \
  -e POSTGRES_DB=theaidb \
  -e POSTGRES_USER=theaiuser \
  -e POSTGRES_PASSWORD='<CHANGE_ME>' \
  postgres:15-alpine
  3. Backend : 
    docker run -d \
  --name theai-backend \
  --network theai-net \
  --network-alias backend \
  -p 8000:8000 \
  -e POSTGRES_SERVER=theai-db \
  -e POSTGRES_USER=theaiuser \
  -e POSTGRES_PASSWORD='<CHANGE_ME>' \
  -e POSTGRES_DB=theaidb \
  -e POSTGRES_PORT=5432 \
  -e SMTP_SERVER=smtp.example.com \
  -e SMTP_PORT=587 \
  -e SMTP_USERNAME='<SMTP_USER>' \
  -e SMTP_PASSWORD='<SMTP_PASSWORD>' \
  -e SMTP_FROM_EMAIL=monitoring@example.com \
  -e SMTP_USE_TLS=true \
  -e ENABLE_EMAIL_ALERTS=true \
  -e ALERT_EMAILS=admin@example.com \
  -e SECRET_KEY='<GENERATE: openssl rand -hex 32>' \
  -e ACCESS_TOKEN_EXPIRE_MINUTES=720 \
  -e DEFAULT_ADMIN_USERNAME=admin \
  -e DEFAULT_ADMIN_PASSWORD='<CHANGE_ME>' \
  -e DEFAULT_ADMIN_EMAIL=admin@theai.local \
  ghcr.io/iwebbo/theai/backend:[TAG]
  4. Frontend : 
    docker run -d \
  --name theai-frontend \
  --network theai-net \
  -p 80:80 \
  -e API_URL=http://<HOST_BACKEND>:8000 \
  ghcr.io/iwebbo/theai/frontend:[TAG]
  5. Ouvrir http://<HOST> et se connecter avec le compte défini par DEFAULT_ADMIN_*.
Secrets. Ne jamais commiter ni documenter de vrais mots de passe, SECRET_KEY ou identifiants SMTP. Utiliser un gestionnaire de secrets (Vault, Kubernetes Secrets, Docker secrets).

5.3 Contrôle SSL/TLS

  • Détection de la version minimale acceptée
  • Signalement des protocoles obsolètes : SSLv2, SSLv3, TLS 1.0, TLS 1.1
  • Validation de la chaîne de certificats
  • Recommandation : TLS 1.2+ avec suites de chiffrement robustes

5.5 Bonnes pratiques

  1. Quick Scans toutes les heures pour une surveillance continue
  2. Full Scans hebdomadaires en fenêtre de maintenance
  3. Suivre l'évolution des vulnérabilités dans le dashboard
  4. Appliquer rapidement les recommandations
  5. Tracer les remédiations (ticket Jira lié)
  6. Utiliser les rapports pour les audits et la conformité
Usage autorisé uniquement. Ne scanner que des systèmes dont vous êtes propriétaire ou pour lesquels vous disposez d'une autorisation écrite.

Documentation interactive : Swagger UI http://<HOST>:8000/docs et ReDoc http://<HOST>:8000/redoc.

Exemple d'appel authentifié 
TOKEN=$(curl -s -X POST http://<HOST>:8000/api/v1/auth/login \
  -d 'username=admin&password=<PASSWORD>' | jq -r .access_token)

curl -s -H "Authorization: Bearer $TOKEN" http://<HOST>:8000/api/v1/servers
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  http://<HOST>:8000/api/v1/security/scan/quick/1

Adapter le format du body de login à l'implémentation réelle (form-data OAuth2 ou JSON).

7. Sécurité de la plateforme

En place
  • Validation et assainissement des entrées
  • Protection injection SQL (SQLAlchemy, requêtes paramétrées)
  • CORS configuré
  • Secrets via variables d'environnement
  • Conteneurs non-root, surface d'attaque minimale
  • Authentification JWT
Limites connues
  • Identifiants SSH stockés en base (chiffrement prévu)
  • HTTP uniquement (terminaison TLS requise)
  • Pas de rate limiting
  • Journalisation des événements de sécurité limitée

Checklist de durcissement avant mise en production

  • ☐ Reverse proxy avec terminaison TLS (HTTPS)
  • ☐ SECRET_KEY unique et aléatoire, compte admin par défaut changé
  • ☐ Segmentation réseau : base non exposée, backend accessible uniquement via le proxy
  • ☐ Rate limiting au niveau du proxy (login notamment)
  • ☐ Volume persistant et sauvegardes PostgreSQL testées
  • ☐ Images épinglées par tag/digest et veille CVE sur les dépendances
  • ☐ WAF envisagé si exposition hors réseau interne

9. Dépannage

Permission refusée pour le ping (ICMP)

Sous Linux, autoriser le ping aux utilisateurs non-root :

sudo sysctl net.ipv4.ping_group_range="0 2000"
Le frontend n'atteint pas l'API
  • Vérifier API_URL : doit être joignable depuis le navigateur du client, pas seulement depuis le conteneur.
  • Vérifier la configuration CORS du backend.
  • Vérifier que le port 8000 est ouvert.
Le backend ne démarre pas
  • Consulter docker logs theai-backend.
  • Contrôler POSTGRES_SERVER et le réseau theai-net.
  • Vérifier que la base est démarrée avant le backend.
Les alertes e-mail ne partent pas
  • Vérifier ENABLE_EMAIL_ALERTS=true et ALERT_EMAILS.
  • Vérifier le flux sortant vers le SMTP (port 587) et SMTP_USE_TLS.
  • Avec Gmail, utiliser un mot de passe d'application.
